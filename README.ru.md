# @hoshinotatsuya/bullmq-kit

[![npm](https://img.shields.io/npm/v/@hoshinotatsuya/bullmq-kit.svg)](https://www.npmjs.com/package/@hoshinotatsuya/bullmq-kit)
[![CI](https://github.com/HoshinoTatsuya/bullmq-kit/actions/workflows/ci.yml/badge.svg)](https://github.com/HoshinoTatsuya/bullmq-kit/actions/workflows/ci.yml)

[English](./README.md) · [Changelog](./CHANGELOG.md)

Модули очередей поверх Redis и BullMQ, выверенные отказами реальной эксплуатации: потолок одновременных задач на группу (`GroupConcurrency`) с ожиданием освобождения, темп на группу (`GroupRateLimit`), общий пул со справедливой долей (`FairShare`), отсрочка задачи BullMQ при упоре в потолок (`acquireOrDelay`), выключение Worker (`WorkerShutdown`), очередь мёртвых, уборка осиротевших хэшей задач (`OrphanedJobsCleanup`) и инспектор очередей (`QueueInspector`).

## Установка

```sh
npm install @hoshinotatsuya/bullmq-kit ioredis
# для входа /bullmq (acquireOrDelay, WorkerShutdown, очередь мёртвых):
npm install bullmq
```

| peer-зависимость | диапазон | кому нужна |
|---|---|---|
| `ioredis` | `^5 \|\| ^6` | всем входам (потолкам годится любой клиент с `eval`) |
| `bullmq` | `^5 \|\| ^6`, необязательная | только `@hoshinotatsuya/bullmq-kit/bullmq` |

Node.js ≥ 24. Пакет — CommonJS с декларациями типов, грузится и из ESM.

## Быстрый старт

```ts
import { ACQUIRE_OUTCOME, GroupConcurrency } from '@hoshinotatsuya/bullmq-kit';
import { Redis } from 'ioredis';

const redis = new Redis(process.env.REDIS_URL ?? 'redis://127.0.0.1:6379');
const slots = new GroupConcurrency(redis, { prefix: 'myapp:tenant-slots' });

export async function handle(tenantId: string, jobId: string): Promise<string> {
  // ttlMs is how long a slot survives a crashed holder, not how long the work takes:
  // withSlot renews the slot every ttlMs / 3 while the work runs.
  const result = await slots.withSlot(
    tenantId,
    `reports:${jobId}`,
    { limit: 3, ttlMs: 30_000 },
    async (signal) => {
      // Long work must listen to `signal`: it is aborted with SlotLostError when the slot is lost.
      signal.throwIfAborted();
      return `report for ${tenantId}`;
    },
  );
  if (result.outcome === ACQUIRE_OUTCOME.limit) {
    // The tenant already runs 3 jobs. retryAfterMs is the worst case (all holders crash), not a schedule.
    throw new Error(`busy, worst-case retry in ${result.retryAfterMs ?? 'never'} ms`);
  }
  return result.value;
}
```

Весь код этого README — выдержки из [`examples/`](./examples): примеры проверяются `pnpm run typecheck` против исходников пакета, а спека `src/readme-examples.spec.ts` краснеет, если блок README разошёлся с примерами. Комментарии в примерах — по-английски.

Это намеренно: `bullmq` — необязательный peer, и корневой вход обязан грузиться в проекте без него (проверено тестом: загрузка корня с запрещённым `bullmq` проходит, загрузка `/bullmq` — нет). ## GroupConcurrency — потолок одновременных задач на группу

Группа — арендатор, проект, IP. Потолок общий для всех реплик: состояние лежит
в Redis, решения принимают атомарные скрипты Lua.

```ts
  // The same with explicit acquire/release.
  const outcome = await slots.acquire(tenantId, jobId, { limit: 3, ttlMs: 10 * 60_000 });
  if (outcome === ACQUIRE_OUTCOME.limit) {
    return;
  }
  try {
    // ... work; renew long work with: await slots.heartbeat(tenantId, jobId, 10 * 60_000)
  } finally {
    await slots.release(tenantId, jobId);
  }
```

### Почему множество держателей, а не счётчик

Счётчик `INCR`/`DECR` нельзя сделать идемпотентным. Снятие приходит из нескольких мест: провал каждой попытки, страховка восстановления, повтор. Лишний `DECR` отдаёт чужой слот. Замер на живом Redis: при потолке 3 работало 5 задач, и в логе не было ни строки.

Здесь группа — ZSET держателей, очко — дедлайн слота:

| Операция | Свойство |
|---|---|
| `acquire` | повторный захват тем же держателем возвращает `held` и слот не тратит; просроченные держатели снимаются тем же вызовом |
| `release` | `ZREM` идемпотентен: повтор ничего не отдаёт |
| `heartbeat` | продлевает только ЖИВОЙ слот (`XX`); после снятия возвращает `false` и мимо потолка слот не занимает |
| упавший держатель | освобождает слот по сроку, а не никогда |
| ключ группы | получает срок по самому позднему держателю: группы задаются внешним вводом, и без срока ключи копились бы |

Время берётся из `TIME` сервера Redis, а не из часов реплики: у реплик часы расходятся.

`reserve(group, holder, { limit, ttlMs })` — резерв слота на подготовку работы: как `acquire`, но слот, который держатель уже держит, НЕ продлевает (`held`, срок прежний). Резерв короче рабочего срока, и продление им укоротило бы слот идущей работы (например, планировщик на каждом обходе резервирует и группу, где работа уже идёт). После подготовки слот переводят на рабочий срок обычным `acquire`.

Исход захвата — `acquired | held | limit`, значениями — `ACQUIRE_OUTCOME` (сравнивать с ним, а не со строкой: своя копия строк у вызывающего — второй словарь той же величины). Ошибка Redis — исключение, а не `false`: «не смогли спросить» и «нельзя» — разные ответы, и политику отказа выбирает вызывающий. Пустая группа, пустой держатель, `ttlMs ≤ 0` и дробный или отрицательный `limit` — отказ до обращения к Redis. `limit: 0` закрывает группу, `Infinity` снимает потолок (держатели при этом всё равно считаются).

### Когда повторять: `acquireDetailed`, `reserveDetailed`

Те же захваты, но исход — `{ outcome, retryAfterMs }`. При `limit` `retryAfterMs` — **худший случай**: через сколько мс слот освободится, если ни один держатель не снимет свой и не продлит (время сервера Redis), то есть время возврата слота после смерти держателей. Считается по тому держателю, чьё истечение действительно открывает слот: при потолке ниже числа держателей (потолок снизили на ходу) ждать надо не первого, а `ZCARD − limit + 1`-го. С продлением (`withSlot`) дедлайн держателя всё время сдвигается на `ttlMs` вперёд, и подсказка почти всегда равна полному сроку: замер (200 работ, потолок 10, работа 20 мс, `ttlMs` 30 с) — подсказка p50 29 996 мс при фактическом ожидании слота p50 560 мс. Ждать по ней — терять пропускную способность на порядки; повторять — по экспоненте от малой задержки (`acquireOrDelay`). `null` — исход не `limit` или группа закрыта (`limit: 0`): по сроку она не откроется никогда. `acquire`/`reserve` возвращают прежнюю строку исхода.

### Работа в слоте: `withSlot`

```ts
  const result = await slots.withSlot(
    tenantId,
    `reports:${jobId}`,
    { limit: 3, ttlMs: 30_000 },
    async (signal) => {
      // Long work must listen to `signal`: it is aborted with SlotLostError when the slot is lost.
      signal.throwIfAborted();
      return `report for ${tenantId}`;
    },
  );
```

Занять, выполнять с продлением каждые `ttlMs / 3`, снять в `finally`. `ttlMs` — время возврата слота после смерти процесса, а не длительность работы.

- **Потеря слота — по времени, а не по ответу.** Работа прерывается `SlotLostError`, если продление ответило «слота нет» ИЛИ не подтверждено `ttlMs − ttlMs/10` с ОТПРАВКИ последнего подтверждённого продления (свой таймер плюс проверка в каждом тике). Запрос в замёрзшую сеть не отвечает ни успехом, ни отказом — ни с `maxRetriesPerRequest: null` (его требует BullMQ), ни с умолчаниями ioredis, — и прежняя проверка «в ветке отказа» не исполнялась: замер через замерзающий TCP-прокси давал двух держателей при потолке 1. Отсчёт от отправки, а не от ответа: срок в Redis поставлен в момент исполнения, а оно не раньше отправки; время ответа опаздывает на RTT в небезопасную сторону. Часы — монотонные (`performance.now()`).
- **Потеря слота — отказ вызова, даже если работа вернула значение** (с 0.9.0): `withSlot` отклоняется `SlotLostDuringWorkError` (подкласс `SlotLostError`; значение работы — `value`, потеря, которую видел сигнал, — `cause`). Работа, которая сигнал не слушает или не может прервать начатый вызов, прежде возвращала `{ outcome: 'acquired', value }` — неотличимо от работы под слотом, хотя в группу уже могли пройти другие. Исход `acquired` теперь значит «вся работа шла под слотом».
- **Single-flight продления:** новое не уходит, пока висит прежнее — офлайн-очередь клиента не копит их и не выпускает залпом после восстановления сети.
- **Снятие в `finally` ограничено сроком слота:** в недоступный Redis оно не держит вызывающего дольше, чем слот прожил бы и без снятия.
- **Исход `held`** (слот уже держал этот держатель — прежний захват или ещё живой повтор той же задачи): `withSlot` его продлевает, но НЕ снимает — снимет тот, кто занял, или он истечёт по сроку. Прежде `withSlot` снимал чужой слот.
- `ttlMs` — не больше 2³¹ − 1 мс (предел таймера Node): больший срок Node молча заменяет на 1 мс, и продление шло бы непрерывно. Отказ до Redis.

### Ждать освобождения, а не опрашивать: `acquireWaiting`

```ts
// Waiting for a slot needs a dedicated subscriber connection.
const slots = new GroupConcurrency(redis, { prefix: '{myapp}:slots', subscriber: redis.duplicate() });
```

```ts
export async function waitForSlot(group: string, holder: string): Promise<unknown> {
  // Queue up and be woken by `release` instead of polling; `limit` after 60 s.
  const result = await slots.withSlot(group, holder, { limit: 3, ttlMs: 30_000 }, async () => 'done', {
    timeoutMs: 60_000,
  });
  return result.outcome === ACQUIRE_OUTCOME.limit ? null : result.value;
}
```

Ожидающие встают в очередь группы (ZSET, порядок прихода), `release` будит ПЕРВОГО ЖИВОГО публикацией его имени в канал группы (ожидающие с истёкшей регистрацией снимаются до выбора): освободился один слот — просыпается один, а не все разом. Свободный слот достаётся ожидающим по порядку: держатель занимает его, только если его место в очереди меньше числа свободных, — пришедший позже ждущего не перехватывает. Слот, освобождённый по сроку (держатель умер) или `clear`, публикации не даёт: его подхватывает страховочная перепроверка (`pollMs`, по умолчанию 1 с, и не позже подсказки). Регистрация ожидающего живёт три перепроверки: умерший ожидающий снимается из очереди, а не держит её. Не дождались за `timeoutMs` или отменили `signal` — исход `limit`, из очереди — сразу, без ещё одной попытки после отмены; сигнал, отменённый ещё до вызова, — `limit` без единой команды Redis. `pollMs` — не больше 2^31 − 1 (предел таймера Node). Отказ подписки (`subscriber` отключён) не запоминается: следующее ожидание подписывается заново.

- `subscriber` — отдельное соединение (`redis.duplicate()`): в режиме подписки соединение других команд не принимает. Без него ожидание — отказ с причиной.
- Обычный `acquire` очередь не соблюдает: смешивать в одной группе можно, но порядок тогда держится только среди ожидающих.
- `release` теперь — скрипт (снять и разбудить первого), а не голый `ZREM`: клиенту нужен только `eval`.
- Замер ниже («Предел»): та же нагрузка, что дала подсказку p50 30 с, — с ожиданием вместо опроса.

### Темп на группу: `GroupRateLimit`

```ts
// 60 calls per minute per API key, bursts up to 60.
const rate = new GroupRateLimit(redis, { prefix: 'myapp:rate' });
export async function callApi(apiKey: string): Promise<boolean> {
  const taken = await rate.take(apiKey, { limit: 60, intervalMs: 60_000 });
  // For a rate the hint is exact: a token is available in exactly retryAfterMs (unless someone else takes it).
  return taken.outcome !== ACQUIRE_OUTCOME.limit;
}
```

Ведро токенов на группу в Redis (время сервера, общее для реплик): внешние API ограничивают ТЕМП, а не параллельность, и потолок одновременных задач пропустил бы сотню коротких запросов в секунду при потолке 3. Ответ — тот же `AcquireResult`, поэтому годится `acquireOrDelay` как есть; подсказка здесь ТОЧНАЯ (`exact: true` — токен будет ровно через столько, если его не возьмёт другой), и `acquireOrDelay` откладывает ровно на неё, а не по экспоненте. Ключ ведра живёт до полного наполнения — пространство ключей из внешнего ввода не копится. `cost` больше ёмкости — отказ до Redis (ждать было бы вечно).

### Общий пул со справедливой долей: `FairShare`

```ts
// One pool of 20 workers; a big tenant cannot starve the small ones that are waiting.
const pool = new FairShare(redis, { prefix: 'myapp:pool' });
export async function inPool(tenantId: string, jobId: string, weight: number): Promise<void> {
  const taken = await pool.acquire('scans', tenantId, jobId, { poolLimit: 20, ttlMs: 60_000, weight });
  if (taken.outcome === ACQUIRE_OUTCOME.limit) {
    return;
  }
  try {
    // ... work
  } finally {
    await pool.release('scans', tenantId, jobId);
  }
}
```

Крупный арендатор не выедает весь пул, пока ждут мелкие. Доля группы — `max(1, ⌊потолок · вес / Σ весов активных⌋)`; активные — те, у кого есть держатели, и те, кто недавно упёрся (ждёт, `waitTtlMs`, по умолчанию 60 с). Группа берёт слот, если пул не полон И она ниже своей доли — либо никто из ЖДУЩИХ не ниже своей: свободное не простаивает, одна группа может занять весь пул, пока другим не нужно. Вытеснения нет: лишнее отдаётся по мере завершения работ. `waitTtlMs` — не меньше интервала повтора задач группы (`maxDelayMs` у `acquireOrDelay`): иначе между повторами она «пропадает», и крупная занимает пул целиком. В Redis Cluster — префикс с хэш-тегом (три ключа одного скрипта).

### Несколько групп сразу: `acquireMany`

`acquireMany(holder, [{ group, limit }, ...], ttlMs)` — один скрипт, всё или ничего: проект И арендатор И IP. Отказ хоть одной группы не меняет НИЧЕГО — ни новых слотов, ни сроков уже занятых (иначе отказавший держал бы слоты в группах, где не работает). `blockedBy` — упёршиеся группы, `retryAfterMs` — максимум по ним (освободиться должны все), `null` — среди них есть закрытая. Повтор группы в списке — отказ до Redis. Снимать — `release` по каждой группе. **Redis Cluster:** ключи одного скрипта обязаны лежать в одном слоте — префикс с хэш-тегом (`{app}:project-slots`), иначе Redis ответит `CROSSSLOT`; все скрипты пакета берут ключи только из `KEYS`. Тег проверяется по правилу самого Redis: от ПЕРВОЙ `{` до первой `}` после неё, пусто — тега нет. Поэтому `app{}{t}` и `{}x{t}` — отказ в конструкторе, хотя `{t}` в них есть: Redis хэшировал бы весь ключ.

### Разбор: `holders`, `clear`

`holders(group)` — живые держатели с остатком срока по возрастанию дедлайна. `clear(group)` — снять всех (зависшие слоты после инцидента); работающие держатели теряют слоты, их `heartbeat` вернёт `false`, и на время их работы потолок превышается. Ответ — сколько живых было снято.

### Метрики: `onOutcome`

`new GroupConcurrency(redis, { prefix, onOutcome: (group, outcome) => counter.inc({ outcome }) })` — вызывается после ответа Redis на каждый захват; у `acquireMany` — по группе с её исходом при успехе и по каждой упёршейся при отказе. Исключение и отклонённый промис хука глотаются: иначе слот, уже занятый в Redis, остался бы у вызывающего, получившего исключение. Метка `group` — внешний ввод: в Prometheus её кладут только при ограниченном числе групп.

### Worker BullMQ: `acquireOrDelay` (`@hoshinotatsuya/bullmq-kit/bullmq`)

```ts
    const holder = `${job.queueName}:${job.id}`;
    // At the limit the job goes to `delayed` with exponential backoff (no attempt spent).
    await acquireOrDelay(job, token, () =>
      slots.acquireDetailed(job.data.tenantId, holder, { limit: 3, ttlMs: 60_000 }),
    );
```

При `limit` задача уходит в delayed (`job.moveToDelayed(now + задержка, token)` + `DelayedError`) — не в failed и без траты попытки. **Задержка — экспоненциальная:** `minDelayMs · 2ⁿ`, где `n` — число уже сделанных отсрочек этой задачи (`attemptsStarted − attemptsMade − 1`); потолок — меньшее из `maxDelayMs` (60 000) и подсказки `retryAfterMs` (худший случай: ждать дольше него бессмысленно); без подсказки (закрытая группа) потолок — `closedGroupDelayMs` (60 000). Добавка — случайная, до `max(jitterMs 250, задержка/4)`: разброс растёт с задержкой, иначе задачи одной волны просыпались бы толпой. Прежде задержка равнялась подсказке, а она с продлением ≈ срок слота: каждая упёршаяся задача ждала ~30 с при слотах, свободных через миллисекунды (замер ниже, «Предел»). Неверные настройки и пустой `token` — отказ ДО захвата (без токена BullMQ подставил бы `'0'`, и `moveToDelayed` прошёл бы без проверки лока). Отказ `moveToDelayed` (лок потерян) пробрасывается как есть.

- **Каждая отсрочка — новый старт задачи:** `attemptsStarted` растёт, и `maxStartedAttempts` Worker'а считает отсрочки наравне со стартами — ставьте его с запасом на них или не ставьте. Попытки (`attemptsMade`) отсрочка не тратит.
- **`maxTotalWaitMs` считается от создания задачи** (`job.timestamp`), то есть включает её намеренную задержку `delay`: задача с `delay: 10 мин` и потолком 5 мин упадёт на первой же отсрочке.

Отдельный вход, а не главный: `bullmq` — НЕОБЯЗАТЕЛЬНЫЙ peer, и проект, которому нужен только `GroupConcurrency`, не тянет его при загрузке пакета. Задача — структурный тип (`moveToDelayed`), а не `Job` из bullmq: у проекта своя копия bullmq. Для `moduleResolution: node` вход описан в `typesVersions`.

Порядок шагов, в котором чаще всего ошибаются: 1) перестать брать новые задачи (`pause(true)`, не дожидаясь идущих — иначе за время дренажа Worker наберёт новых); 2) ждать НАЧАТЫЕ задачи до дедлайна — учёт обёрткой процессора, а не событиями (отложенная `DelayedError` задача не шлёт ни `completed`, ни `failed`); 3) дедлайн вышел — прервать сигнал задач (`ShutdownDeadlineError`), дать им `abortGraceMs` (1 с) и `close(true)`; успели — обычный `close()`; 4) отчёт `{ drained, interrupted, durationMs }`. Прерванные задачи будут сделаны повторно другим воркером (stalled) — их id и отдаются. Сигнал самого BullMQ (отмена задачи) переносится в сигнал обёртки событием, а не `AbortSignal.any`: в BullMQ 5.72 он не нативный `AbortSignal`, и `AbortSignal.any` ронял каждую задачу (найдено прогоном `test:oldest`). Задача, которую Worker взял уже после начала выключения (BullMQ не отменяет паузой начатого блокирующего ожидания), не выполняется: отдаётся обратно (`moveToDelayed` через `handBackDelayMs`, 1 с, — не «на сейчас», иначе этот же Worker брал бы её по кругу) и названа в `handedBack`. `deadlineMs` — меньше grace-периода пода с запасом на `close`: после него придёт SIGKILL. `deadlineMs`, `abortGraceMs`, `handBackDelayMs` — числа от 0 до 2^31 − 1 мс (больше и `NaN` Node молча превращает в 1 мс): иначе отказ до первого шага, и он не запоминается — повтор с верными настройками выключает. Повторный `close` — тот же отчёт.

### Очередь мёртвых: `attachDeadLetter`, `retryDeadLetter` (`/bullmq`)


```ts

  for (const entry of await dead.getJobs(['wait'])) {
```

Задача, провалившаяся ОКОНЧАТЕЛЬНО (попытки кончились или `UnrecoverableError`), копируется в очередь мёртвых с причиной, стеком, числом попыток и исходными данными — иначе failed удаляется политикой хранения вместе с причиной. Окончательность — по состоянию задачи (`failed`), а не по событию: событие `failed` Worker шлёт на каждую проваленную попытку. id копии детерминирован (очередь, id, момент провала) — повтор события не плодит копий. Копия — по событию процесса: упавший между провалом и копией процесс её не сделает; это помощник разбора, а не гарантия доставки. `retryDeadLetter`: исходная ещё в failed — её `retry()` (тот же id); удалена политикой хранения — добавляется заново с тем же id и безопасными opts (`DEAD_LETTER.RETRY_OPTS`: без `repeat`, `delay`, `parent`); есть и не в failed — отказ (повтор задвоил бы её).

### Переход с самописных реализаций

- **Дефекты, которые пакет закрывает.** `heartbeat` истёкшего слота занимает его заново по потолку (`ZADD` без `XX` воскрешал слот мимо потолка); «уже держит» проверяется раньше потолка (иначе повтор держателя при полном потолке получал отказ); предпроверка без продления занятого слота — `reserve`.
- **Чего в пакете нет.** Режима без срока держателя (срок держит весь ключ группы и продлевается активностью) — для задач, которые штатно ждут дольше любого порога. Второго ключа — индекса адресов — и отдачи слота через cooldown. Штрафов и cooldown по IP и хосту: это другой механизм.

- **Ключ — новый.** Команды ZSET по прежнему строковому ключу счётчика отвечают `WRONGTYPE` на каждый вызов сразу после выкатки, а очки прежних ZSET — по часам реплики или время захвата, а не дедлайн по `TIME` сервера. Старые ключи просто истекут.
- **Проверять на настоящем Redis, а не на ioredis-mock:** Lua ioredis-mock считает в 32-битных целых, `TIME × 1000` переполняется и даёт отрицательное «сейчас» — срок слотов на подделке не работает вовсе.

## Уборка осиротевших хэшей задач (`/orphan-cleanup`)

Хэш задачи, на который не ссылается ни один индекс статуса (рассинхрон при обрыве соединения посреди перехода), — сирота.

### Версия BullMQ

Уборка удаляет ключи и знает раскладку BullMQ, поэтому перед каждой очередью читает `<очередь>:meta`, поле `version` (`bullmq:X.Y.Z`, его пишет каждый `new Queue`). Очередь вне проверенного диапазона — **не убирается**, а называется в `report.unsupportedQueues` и в журнале. Нет поля — тоже отказ: «не смогли определить» не означает «знакомая раскладка».

Диапазон — `BULLMQ_SUPPORTED_VERSIONS.RANGES`, по одному на проверенный мажор: **5.72.0 … 5.81.x** и **6.0.0 … 6.7.x** (`MIN` — нижняя граница, `MAX_MINOR` — последний проверенный минор, патчи внутри него принимаются). Все четыре границы проверены, а не заявлены: `pnpm test` гоняет весь набор против каждой (`test:oldest` — 5.72.0, `test:bullmq5` — последняя 5, `test:bullmq6-oldest` — 6.0.0, `test:latest` — последняя 6; псевдонимы в devDependencies). Младше 5.72.0 нет `keepLastIfActive` (ключ `dn:`), и на 5.71.1 набор красный. Верхняя граница — минор, а не мажор: служебные ключи BullMQ вводит в минорах (`dn:` — 5.72, `repeat:` job schedulers — 5.16, relay — 6.x). Тест держит каждую границу равной версии псевдонима, против которого идёт набор: подъём devDependency без подъёма границы — красный. Мажор вне списка (7, 4) — отказ. Предрелиз младше своего релиза: `5.72.0-beta.1`, `6.0.0-beta.1` — отказ.

**BullMQ 6 против 5** — сверено по исходникам (Lua и `QueueKeys` установленных 5.81, 6.0 и 6.7) и прогоном набора: имена и типы ключей очереди те же, хэш задачи, `de:`/`dn:` и хвосты пишутся теми же полями. Отличия, которые уборка учитывает:
- пауза больше не переносит `wait` в список `paused`: задачи приостановленной очереди остаются в `wait`. Список `paused` — наследство очередей, поставленных на паузу BullMQ 5 (BullMQ 6 возвращает его в `wait` при `resume`); уборка по-прежнему проверяет его — задачи в нём живы;
- relay BullMQ 6 держит ключи в `<prefix>::relay:{<ns>}:…` — с ПУСТЫМ сегментом после префикса, вне пространства очередей `<prefix>:<имя>:…`. Но если префикс relay совпал с префиксом очереди (`bull:orders`), его ключи лежат ВНУТРИ её пространства, и хэши узлов и удержанных сообщений (без `timestamp`) с `deleteUntimestamped` удалялись бы по второму наблюдению (проба на 6.7.7). Поэтому ключ с пустым сегментом сразу после префикса очереди (`<очередь>::…`) кандидатом не становится никогда.

Словарь ключей сверяется с `QueueKeys.getKeys()` установленной BullMQ в каждом прогоне (на нём построен и `Queue.removeOrphanedJobs` самой BullMQ), а индексы статусов — с ключами настоящей очереди, в которых лежат id задач во всех состояниях: новый индекс в BullMQ — красный тест, а не удалённые живые задачи.

### Поведение

| | библиотека | почему |
|---|---|---|
| `waiting-children` в индексах | есть | без него хэш родителя flow-задачи, ждущего детей, удаляется как сирота |
| jobId с `:` | допустим; служебные хвосты узнаются регуляркой | пропуск любого суффикса с `:` прятал бы сирот с таким jobId |
| TTL на живые хэши | **нет** | при неограниченном ожидании в очереди TTL теряет тело задачи |
| несколько очередей с общим бюджетом | да | один прогон не растягивается на число очередей |
| подтверждение перед удалением | проверка и удаление одним скриптом Lua на хэш | между проверкой и удалением задача не может появиться в индексе |
| очередь, чей префикс вложен в убираемую | **отказ на всю очередь** + проверка в скрипте на каждого кандидата | префикс BullMQ может содержать `:`: очередь `x` с префиксом `bull:jobs` живёт ключами `bull:jobs:x:*`, и её живые задачи по индексам `bull:jobs` неотличимы от сирот |
| хэш без `timestamp` | **не удаляется** (опция `deleteUntimestamped`) | так выглядит и служебный хэш версии BullMQ, которой уборка не знает |
| ключ `<очередь>::…` (пустой сегмент после префикса) | **не кандидат** | так BullMQ 6 отделяет relay; при префиксе relay, равном префиксу очереди, его хэши лежат внутри её пространства. Задача с id, начинающимся с `:`, лишь не убирается |

Про TTL. Если ожидание задачи в очереди не ограничено, TTL на хэш теряет тело задачи на проде. Если проект ограничивает ожидание расчётом, TTL (например, 24 ч) безопасен — тогда он остаётся отдельным механизмом проекта. Сама библиотека TTL не ставит: безопасный срок — знание проекта, а не уборки.

### Проверка и удаление — один скрипт

Кандидат в сироты (его нет в снимке индексов) проверяется и удаляется ОДНИМ скриптом Lua на хэш, скрипты батча идут одним пайплайном. В скрипте, по порядку:

1. ключ — хэш (`TYPE` внутри скрипта: поштучных TYPE с клиента больше нет);
1. ключ не принадлежит вложенной очереди: для каждого `:` в jobId префикс до него проверяется как очередь BullMQ — хэш `P:meta` с полем `version` или `opts.maxLenEvents`, либо строка `P:id` (их пишет каждое добавление задачи). Найдено — «вложенная» (`kept.nested`), не удаляется. Это рубеж для усечённого обхода; полный обход, увидевший `P:meta`/`P:id`, отказывает всей очереди до удаления (`unsupportedQueues` с причиной);
2. у задачи нет живого `:lock` — иначе «под локом» (`kept.locked`): её держит воркер, O(1) рубеж независимо от того, успел ли переход попасть в индекс;
2. id нет ни в одном индексе: `prioritized`, `delayed`, `completed`, `failed`, `waiting-children` (ZSCORE), `stalled` (SISMEMBER), затем `wait`, `active`, `paused` (LPOS). Списки — последними: LPOS отсутствующего id проходит список целиком (замер на Redis 7.4: 15 мс блокировки на миллион элементов), а задача из огромного `completed` вне снимка находится ZSCORE и списков не касается. Тип индекса берётся `TYPE`: индекс неожиданного типа — «не смогли проверить», хэш НЕ удаляется (`kept.unverifiable`);
3. хэш старше грейса по полю `timestamp` против времени сервера Redis (`graceMs`, по умолчанию 60 с; из будущего — тоже «молод»). Поле не число — возраст неизвестен, не удаляется. **Положительная форма:** хэш с `timestamp` удаляется, только если в нём есть `name` и `opts` — их storeJob.lua пишет тем же HMSET (`kept.notJob` — нет). Поля `timestamp` нет — так выглядит поздняя запись в удалённую задачу, но так же и служебный хэш версии BullMQ, которой уборка не знает: **по умолчанию не удаляется никогда** (`kept.untimestamped`); с `deleteUntimestamped: true` — по второму наблюдению не раньше грейса;
4. id не ждёт отложенная задача дедупликации: `dn:<deid>` с `jid` = этот id — «жива»;
5. удаление хэша и хвостов `:logs`, `:dependencies`, `:processed`, `:failed`, `:unsuccessful` — ровно то, что удаляет сам BullMQ (removeJobKeys.lua). **`:lock` не удаляется никогда**: лок значит, что воркер, возможно, ещё держит задачу; он истечёт сам;
6. ключ дедупликации `de:<deid>`, указывающий на удалённую сироту, снимается вместе с `dn:<deid>` — как при удалении задачи самим BullMQ. Иначе id дедупликации был занят бы навсегда (без ttl и с keepLastIfActive ключ без срока): каждая новая задача молча «дедуплицировалась» бы в несуществующую.

Прежде проверка шла пайплайном ZSCORE/LPOS, затем TYPE поштучно, затем отдельный DEL — между проверкой и удалением задача могла появиться в индексе. Второй полный снимок индексов убран: проверка в скрипте строже и не перечитывает индексы.

Ключи, известные заранее, — в `KEYS`; `de:`/`dn:` скрипт собирает из префикса очереди (id дедупликации известен только внутри), как и сам BullMQ. В Redis Cluster BullMQ работает только с хэш-тегом в префиксе — те же ключи в том же слоте. Проба на Redis 7.4 в режиме кластера: необъявленный ключ того же слота скрипт читает и удаляет (и без shebang, и с `#!lua`); отказ — только для ключа другого слота или чужого узла, отказа «non declared key» в Redis нет. Dragonfly необъявленные ключи по умолчанию отвергает, но BullMQ там и сам требует `--default_lua_flags=allow-undeclared-keys`.

**Flow.** BullMQ 5.81 ключей `:children` и `:parent` не создаёт: связь — поля `parentKey`/`parent` в хэше ребёнка и хвосты родителя `:dependencies`, `:processed`, `:failed`, `:unsuccessful`. Каждый хэш дерева лежит в индексе статуса (родитель — в `waiting-children`, дети — в своих). Тест на настоящем дереве (внук и ребёнок выполнены, второй ребёнок отложен) проверяет, что среди ВСЕХ ключей очереди фильтр делает кандидатами ровно четыре хэша дерева.

**Не поддерживается: BullMQ Pro (группы).** По описанию Pro задачи групп лежат в собственных ключах групп, а не в `wait`; библиотека этих индексов не знает и сочла бы такие задачи сиротами. Не проверялось на Pro — не подключать к его очередям.

### Настройки

|---|---|---|

| `maxScannedKeysPerRun` | 200 000 | потолок ключей SCAN вместе с хвостами: хвостов бывает во много раз больше задач |
| `maxRunMs` | 60 000 | потолок длительности: SCAN с MATCH по Redis на десятки миллионов ключей обходит все, а совпадений мало |

| `maxListScan` | `1 000 000` (с 0.9.0; прежде `Infinity`) | потолок элементов списка, которые LPOS просматривает на кандидата (`MAXLEN`). Умолчание — из замера (раздел «Предел»). «Без потолка» — только явным `Infinity`. `0` — отказ в конструкторе: `MAXLEN 0` Redis понимает как «весь список» |
| `reportKeysLimit` | 100 | сколько ключей сирот вернуть в `orphanKeys` |
| `logger` | — | `{ log, warn, debug? }` (совместим с `Logger` Nest): строка на сироту (debug), итог (log), усечение, непроверенные, крупные индексы (warn) |
| `scanClients` | основной клиент | Redis Cluster: SCAN обходит один узел — передайте мастера. Курсор хранится на объект узла: курсор одного узла не применяется к другому. Проверка и удаление — через основной клиент. Пустой список — отказ |
| `maxSnapshotListSize` | 1 000 000 | список статуса длиннее — очередь в этом прогоне не убирается (`unsnapshottedIndexes`): снимок держит id в памяти процесса, 10 млн id в `wait` — сотни МБ. `Infinity` — без потолка; конечный требует `llen` у клиента |
| `maxListWorkPerBatch` | 1 000 000 | батч удаления уменьшается так, чтобы «кандидатов × длина списков статусов» не превышала потолок: пайплайн Redis исполняет подряд, и 100 сирот при `wait` на миллион держали бы его 1.5 с (LPOS — 15 мс на миллион) |
| `runLockKey` | — | лок прогона `SET NX PX` на `maxRunMs` + 30 с: реплики с одним расписанием иначе делают ту же работу N раз. Занят — `lockedOut: true`, снимается только свой |

Между батчами SCAN, страницами снимка и батчами удаления процесс уступает цикл событий `setImmediate` (а не `await Promise.resolve()`, который не пропускает ни таймеры, ни ввод-вывод). Нулевой `batchSize`/`snapshotPage` — отказ в конструкторе, а не вечный цикл.

Отчёт: `scanned`, `deleted`, `durationMs`, `highOrphanShare`, `scannedKeys`, `orphans`, `orphanKeys`, `dryRun`, `kept` (`alive`, `locked`, `young`, `unknownAge`, `notHash`, `unverifiable`, `untimestamped`, `notJob`, `nested`, `errors` — причины «не удалили» различимы; ошибка команды в ответе пайплайна — `errors`, а не удалено), `keptKeys` (выборка ключей до `reportKeysLimit` по каждой причине), `truncatedBy` (`jobs` | `keys` | `time` | `null`, `CLEANUP_STOP_REASON`), `unsnapshottedIndexes`, `unsupportedQueues`, `lockedOut`.

**Режим отчёта для первого включения** на незнакомой инсталляции: `dryRun: true` — `orphanKeys` (что удалилось бы) и `keptKeys` (что и почему осталось) по категориям, ничего не удаляя.

Прочее о прогоне:
- **Скрипты — по SHA (`EVALSHA`):** скрипт проверки — ~2.5 КБ текста, и `EVAL` слал его на каждого кандидата. `NOSCRIPT` (рестарт Redis, `SCRIPT FLUSH`, failover) — повтор этих вызовов через `EVAL`, который заодно кладёт скрипт в кэш. Клиент без `evalsha` — прежний `EVAL`.
- **Курсор не зацикливается:** место остановки по потолку — курсор порции SCAN И число уже просмотренных ключей в ней. Прежде порция с хэшами больше `maxJobsPerRun` начиналась каждый прогон с начала, и её хвост не просматривался никогда.
- **Одновременные `run()` одного экземпляра — один прогон:** второй вызов получает отчёт идущего. Между репликами — `runLockKey`.

### Инспектор очередей (`/inspect`)

```ts
const inspector = new QueueInspector(new Redis(), { queuePrefixes: ['bull:emails', 'bull:reports'] });

createServer((_request, response) => {
  inspector.inspect().then(
    (health) => {
      response.setHeader('content-type', 'text/plain; version=0.0.4');
      response.end(toPrometheus(health));
    },
```

Снимок очереди — ОДНИМ скриптом (согласованно и по времени сервера): счёт каждого индекса; пауза (`paused`, поле `meta.paused` — его пишут BullMQ 5 и 6); активные без `:lock` (лок истёк — воркер умер или не продлевает; растущее число — воркеров нет) — просмотр `maxActiveScan` САМЫХ СТАРЫХ active с хвоста списка (воркер ставит новую задачу в голову); возраст самой старой ждущей — по `wait` и `paused` (BullMQ 5 на паузе держит ждущих в `paused`); индексы не своего типа (`unexpectedTypes`, метрика `_unexpected_type_keys`) не читаются и называются — их счёт 0 значит «не прочитано», а снимок остальных очередей не падает; насколько опоздала проснуться самая ранняя отложенная (растёт — некому переводить delayed в wait); прирост failed с прошлого снимка этого экземпляра; сироты — уборкой в dryRun (`orphans: true`, это SCAN всего пространства — включать реже). Только чтение. Неизвестное — `null` и в метрики не выводится: «ноль» и «не мерили» — разные ответы. Метки экранируются по формату экспозиции; `group`-подобных меток нет — только имя очереди.

**Пауза на BullMQ 6.** Ждущие приостановленной очереди остаются в `wait` (BullMQ 5 переносила их в `paused`): `counts.wait` растёт, `counts.paused` — ноль, и `oldestWaitAgeMs` растёт, как у очереди без воркеров. Правило алерта на возраст ждущих исключает очереди с `paused: true` (метрика `bullmq_queue_paused`); на BullMQ 5 то же правило работает без изменений.

Замер `bench/orphan-cleanup.cjs` (`pnpm build && scripts/with-redis.sh node bench/orphan-cleanup.cjs`): Redis 7.4 в docker на ноутбуке; очередь — 100 тыс. хэшей задач (90 тыс. в `completed`, 10 тыс. сирот), рядом 1 млн чужих ключей; задержку Redis меряет PING с другого соединения во время прогона.

|---|---|---|---|
| списки статусов пусты | 1.3 с | 78 тыс. | 0.36 / 3.3 / 5.4 мс |
| `wait` на 100 тыс. | 12.1 с | 8.2 тыс. | 9.9 / 15 / 41 мс |

- Чужие ключи почти бесплатны: SCAN с MATCH прошёл 1.1 млн ключей, прогон уложился в 1.3 с.
- **Цена — сироты × длина списков статусов.** Проверка сироты в скрипте делает LPOS по `wait`, `active`, `paused`, и отсутствующий id проходит список целиком: ~1 мс на сироту на 100 тыс. элементов (здесь 10 тыс. сирот × 100 тыс. = +10.8 с). Всё это время Redis занят скриптами, и соседние команды ждут: p50 PING вырос в 27 раз.
- Когда это опасно: очередь с длинным `wait` (отставание обработки) и массовым рассинхроном одновременно — то есть ровно в аварию. Потолок даёт `maxListScan` (сироты при длинном списке остаются до его сокращения, `kept.unverifiable`) или меньший `maxJobsPerRun` (цена делится на прогоны).

**Потолок `maxListScan` — замер для умолчания** (`node bench/orphan-cleanup.cjs list-scan` и `list-scan-beyond` под `scripts/with-redis.sh`, Redis 7.4 в docker на ноутбуке, 21.11.2026). 20 тыс. хэшей, из них 2 тыс. сирот; ни одной сироты нет в `wait`, то есть LPOS каждой идёт до потолка — худший случай. PING с соседнего соединения каждые 2 мс; по три повтора на точку, p99 — разброс повторов.

| 3 млн, `maxSnapshotListSize: Infinity` | 1 млн | 4.9 с | 0 / 300 | 7.7 мс | 9.5 мс (max 16 мс) |

- До миллиона p99 соседа не зависит от потолка: пайплайн удаления и так ограничен `maxListWorkPerBatch` (~15 мс работы на пайплайн), и между пайплайнами Redis отвечает другим. Цена длинного `wait` — длительность прогона и p50 (Redis занят почти всё время прогона), а не p99.
- Не делит ничто только ОДИН скрипт: LPOS по списку длиннее миллиона идёт целиком в одной команде. Это видно лишь при снятом потолке снимка (`maxSnapshotListSize` по умолчанию тоже миллион): на 3 млн без потолка p99 соседа 31 мс, max 51 мс.
- Отсюда умолчание 1 млн: в пределах снимка по умолчанию поведение то же, что без потолка (все сироты удаляются), а снятый потолок снимка больше не открывает неограниченный скрипт. Потолок 100 тыс. снижал p99 при `wait` в миллион с ~12 до ~5 мс, но оставлял неубранными ВСЕ сироты любой очереди с отставанием больше 100 тыс.; кому важнее p99, чем уборка во время отставания, — задать его явно.

- **Почему не «искать только у концов списка».** Новые задачи входят в `wait` с головы (`LPUSH`) или хвоста (`RPUSH` при `lifo`), и окно у концов выглядит достаточным. Но снимок длинного списка читается страницами, неатомарно: `LREM` посреди списка во время чтения (удаление задачи, `promote`, `changePriority`) сдвигает элементы из непрочитанной части в прочитанную. Задача, давно лежащая в середине, не попадёт в снимок, её `timestamp` старый, грейс её не держит, и найдёт её только полный LPOS в скрипте удаления. Поэтому полный LPOS — рубеж, а не неэффективность; цену ограничивают `maxListScan` и `maxJobsPerRun`.

## Предел `GroupConcurrency`

Замер `bench/capacity.cjs` (`pnpm build && scripts/with-redis.sh node bench/capacity.cjs`): Redis 7.4 в docker на ноутбуке, клиенты ioredis в одном процессе. Пара — `acquire` + `release` (отказ `limit` — один скрипт).

| вызывающих | одна группа, потолок 10 | 10 тыс. групп, потолок 10 |
|---|---|---|
| 1 | 2.6 тыс. пар/с, p99 1.3 мс | 2.7 тыс./с, p99 1.1 мс |
| 8 | 8.2 тыс./с, p99 2.7 мс | 8.6 тыс./с, p99 2.2 мс |
| 32 | 24 тыс./с, p99 4.1 мс | 19 тыс./с, p99 4.4 мс |
| 128 | 42 тыс./с, p99 7.3 мс | 36 тыс./с, p99 7.2 мс |

- **Число держателей группы на цену не влияет:** захват при 0, 1 000 и 100 000 держателях — p50 0.18 мс, p99 до 0.9 мс (ZSET: снятие просроченных и `ZCARD` логарифмичны). Исключение — момент, когда истекают сразу все держатели большой группы: их снимает первый следующий вызов, разово O(N).
- **Память:** 141 байт на группу с одним держателем (100 тыс. групп — 13 МБ). Группы с ключом из внешнего ввода живут не дольше срока самого позднего держателя, поэтому память ограничена темпом новых групп × `ttlMs`, а не их общим числом.
- **Потолок — один поток Redis:** все решения — скрипты на одном узле. В Redis Cluster префикс с хэш-тегом кладёт ВСЕ группы на один шард, так что кластер предел не поднимает; поднимают его разные префиксы (разные `GroupConcurrency`) на разных шардах.
- Каждая работа в `withSlot` добавляет продление раз в `ttlMs / 3`: 10 тыс. одновременных работ при `ttlMs` 30 с — ещё 1 тыс. скриптов/с.

**Повтор под потолком: подсказка против экспоненты и ожидания.** Одна горячая группа, потолок 10, работа 20 мс, `ttlMs` 30 с, 200 работ — ровно то, при чём подсказка `retryAfterMs` (худший случай) почти равна сроку слота.

|---|---|---|---|
| `acquireOrDelay` 0.5.1 (задержка = подсказка), BullMQ 5.81, Worker concurrency 50 | 90.9 с | 60.2 с / 90.7 с | 497 захвата + 2 184 BullMQ |
| `acquireOrDelay` 0.6.0 (экспонента от 100 мс) | 2.5 с | 0.57 с / 2.3 с | 771 захват + 1 543 BullMQ |
| `withSlot`, повтор опросом min(50 мс, подсказка) (0.5.1 и 0.6.0 одинаково; подсказка p50 29 997 мс) | 1.06 с | 0.56 с / 1.04 с | 2 100 (1 900 отказов `limit`) |
| `withSlot(..., { timeoutMs })` 0.6.0 — ожидание освобождения | 0.47 с | 0.24 с / 0.45 с | 590 |

Замер: `bench/acquire-or-delay-load.cjs` и `bench/slot-wait-load.cjs` (`pnpm build && scripts/with-redis.sh node bench/<скрипт> <dist> 200 10 20 30000 [poll|wait]`), Redis 7.4 в docker на ноутбуке. Теперь занявший будит следующих по числу оставшихся свободных.

## Гарантии и ограничения

- **Атомарность:** каждое решение `GroupConcurrency`, `GroupRateLimit`, `FairShare` и каждая проверка-с-удалением уборки — один скрипт Lua; время — `TIME` сервера Redis, а не часы реплики.
- **Снятие идемпотентно** (`ZREM`), упавший держатель освобождает слот по сроку.
- **Пространство ключей ограничено:** ключ группы живёт до срока самого позднего держателя, ведро темпа — до наполнения; память — темп новых групп × `ttlMs`, а не их общее число.
- **Потолок пропускной способности — один поток Redis** (замеры — «Предел `GroupConcurrency`»); хэш-тег кладёт все группы префикса на один шард кластера.
- **`retryAfterMs` — худший случай**, а не расписание.
- **Цена уборки — сироты × длина списков статусов**; потолки — `maxListScan`, `maxListWorkPerBatch`, `maxJobsPerRun` (замеры — «Предел» уборки).
- **Копия в очередь мёртвых — по событию процесса**, это помощник разбора, а не гарантия доставки.
- **Тексты ошибок, строки журнала и `HELP` метрик — по-русски.** Программные поля (`outcome`, `reason`, поля отчётов, классы ошибок) стабильны; разбирать текст сообщений не нужно.
- Не делается намеренно: обёртка над всем API BullMQ; собственный планировщик повторяющихся задач (в BullMQ есть job schedulers); держатель без срока; вытеснение в `FairShare`.

## Поведение при отказах

Пакет отказывает закрыто — «не смогли определить» не означает «можно»:

- ошибка Redis — исключение, а не `false`: «не смогли спросить» и «нельзя» — разные ответы, политику выбирает вызывающий;
- неверные аргументы (пустая группа или держатель, `ttlMs ≤ 0` или больше 2³¹ − 1, дробный или отрицательный `limit`, `cost` больше ёмкости, префикс без хэш-тега в кластере, пустой `queuePrefixes`, нулевые размеры батчей) — отказ ДО обращения к Redis или в конструкторе;
- уборка при сомнении не удаляет: незнакомая или отсутствующая версия BullMQ, вложенная очередь, индекс не своего типа, слишком длинный для проверки список, нечисловой или отсутствующий `timestamp`, хэш без `name`/`opts` — хэш остаётся и посчитан в `kept` или `unsupportedQueues`;
- `withSlot` считает неподтверждённое продление потерей слота через `ttlMs − ttlMs/10`, прерывает работу и отказывает, даже если работа вернула значение.

- Всё, что зависит от Redis, — против настоящего Redis 7.4 и настоящей BullMQ: атомарность, срок слота, время сервера, раскладку ключей пишет сама BullMQ.
- Отказы — внедрением: замерзающий TCP-прокси (`src/testing/freezing-tcp-proxy.ts`: сокет открыт, байты не идут) в обоих режимах клиента ioredis; отказ продления; `SCRIPT FLUSH` (NOSCRIPT); подменённые ответы скриптов; ошибка в ответе пайплайна.
- Утверждения о времени — порядком событий и значениями от Redis, а не часами теста (гейт `specsDoNotTimeWithWallClock`): «A заметил потерю» раньше «B занял слот»; ожидающий получил слот при перепроверке раз в минуту — значит, разбудила публикация.
- Каждая правка 0.6.0 проверена мутацией по числу упавших тестов: снятая правка обязана краснеть. Так найдены и закрыты слабые тесты: вложенная очередь без `meta` (признак `id`), удаление хэшей без `timestamp` «по умолчанию» (тест передавал опцию явно), пауза Worker при одном месте, гонка блокирующей выборки BullMQ после паузы.
- Словарь ключей — против `QueueKeys.getKeys()` установленной BullMQ в каждом прогоне и против ключей настоящей очереди, в которых лежат id задач во всех состояниях.
